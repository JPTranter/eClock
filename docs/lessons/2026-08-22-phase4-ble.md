# Phase 4 (BLE) — Final Session Log

> **Date:** 2026-08-23
> **State:** Completed — BLE time sync fully working end-to-end.

## Core Switch & Abandoned Approach

The attempt to use the `Adafruit` core and `Bluefruit52Lib` (or even raw `sd_ble_*` SoftDevice calls) was completely **abandoned**. Despite flashing the Adafruit bootloader, `Bluefruit.begin()` and underlying SDK calls consistently hung or hard-faulted the CPU.

**The Fix:** We switched the firmware to use the **`mbed` core** (`framework-arduino-mbed-seeed`) alongside the standard **`ArduinoBLE`** library. This immediately resolved the hard faults and allowed the BLE stack to initialize successfully.

## Bugs Resolved in This Session

With the `mbed` core running, we encountered and fixed several deep bugs to get the system fully working:

### 1. ArduinoBLE `mbed` Advertisement Bug
When the clock timed out and called `BLE.stopAdvertise()`, a subsequent manual button press called `BLE.advertise()` but the clock remained invisible.
**Fix:** On `mbed`, restarting an advertisement silently fails unless the GAP parameters (`BLE.setLocalName`, `BLE.setDeviceName`, `BLE.setAdvertisedService`) are explicitly re-applied immediately before calling `BLE.advertise()`.

### 2. Time Sync Display Drift
The clock was drifting up to 59 seconds immediately after a sync. The display update logic was blindly counting 60 seconds from the exact moment the BLE packet arrived, ignoring the actual second count of the received UNIX epoch.
**Fix:** Added `g_second = local_time % 60;` and aligned the minute display updates to strictly trigger when `g_second == 0`.

### 3. Millis() Unsigned Underflow
The timeout logic `millis() - g_sync_attempt_start >= SYNC_TIMEOUT` instantly evaluated to true if `g_sync_attempt_start` was recorded slightly *after* `now` was captured in the loop.
**Fix:** Updated the timeout loop to evaluate `millis() - g_sync_attempt_start` inline to guarantee chronological subtraction.

### 4. Font Shearing & Vertical Alignment
The `Adafruit_GFX` generated fonts were displaying with diagonal shearing.
**Fix:** Rewrote `tools/gfxfont_gen.py` to pack bits contiguously instead of row-padding them, regenerated `FontLarge7b.h`, and centered the baseline using `- ty` from `getTextBounds`.

### 5. Home Assistant Discovery Flakiness & UUID Conflicts
Home Assistant's `async_discovered_service_info` cache was dropping the device name if it missed a scan response packet, causing auto-syncs (which originally relied on an exact `name` match) to fail.
**Fix:** We initially switched the HA component's `BluetoothCallbackMatcher` to match the standard Current Time Service UUID (`1805`) instead. However, this caused conflicts with other devices (like Apple Watches) advertising the same generic service.
**Final Fix:** Updated the integration to accept a `mac_addresses` array in `configuration.yaml`. This allows the integration to explicitly filter advertisements by MAC address, guaranteeing it only syncs with the exact clock hardware and bypasses name-resolution flakiness entirely.

### 6. Home Assistant GATT Caching (`was not found` error)
When iterating on the firmware, the HA integration would connect but throw a `BleakError: Characteristic 00002a2b... was not found!` even when the characteristic was perfectly defined in the firmware.
**Root Cause:** Home Assistant (and Linux BlueZ) heavily caches GATT profiles based on the device's MAC address. Because the board was flashed with previous firmware during development, HA remembered the old characteristic list and skipped discovery.
**Fix:** Added `await client.clear_cache()` inside the HA integration right before attempting to write to the GATT characteristic, forcing HA to freshly discover the updated services from the clock.

### 7. Home Assistant Advertisement Deduplication (Silent Failures)
After a successful first sync, pressing the clock's button to initiate a manual sync resulted in nothing happening on the HA side, with completely empty logs.
**Root Cause:** Home Assistant aggressively deduplicates BLE advertisements to save CPU. Since the clock stopped advertising and then started again with the *exact same payload* within the scanner's cache window, HA silently ignored the duplicate packets and never fired the python callback.
**Fix:** Modified the clock firmware to include a rolling counter inside the `ManufacturerData`. Because the advertisement payload now changes by 1 byte every time a sync is requested, HA treats it as a brand-new advertisement and instantly triggers the callback.

## Final Status
Phase 4 is complete. The ePaper clock successfully broadcasts, avoids deduplication filters by using a rolling counter, and Home Assistant explicitly targets it by MAC address, flushes the GATT cache, pushes the UNIX epoch, and the clock updates its display accurately.
