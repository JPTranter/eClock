# Font Generation for eClock

> How to pick the right font size, generate glyph data, and fit it on the
> 296×128 ePaper display. Written for the next developer (human or AI)
> who needs to swap the time font.

## Quickest path: font_tool.py (recommended)

The all-in-one tool at `firmware/tools/font_tool.py` wraps the entire
workflow — sizing scan → generation → centering math — in a single
command. It depends on Pillow (`pip install Pillow`).

```bash
# Step 1: Scan sizes
python firmware/tools/font_tool.py scan "C:/path/to/font.ttf"

# Step 2: Generate header at the recommended size
python firmware/tools/font_tool.py generate "C:/path/to/font.ttf" 82 \
    firmware/src/FontName.h \
    --copyright "Copyright (c) 2024, Type Foundry"

# Step 3: Check centering from an existing header
python firmware/tools/font_tool.py center firmware/src/FontName.h
```

The `generate` command prints the exact `setCursor` line to paste into
`drawClockFace()`, shows width checks for common time strings, and
detects whether the colon needs yOffset adjustment.

## Toolchain (low-level)

```
TrueType (.ttf)  ──→  gfxfont_gen.py  ──→  GFXfont header (.h)
```

The low-level generator lives at `firmware/tools/gfxfont_gen.py`.
Usage:

```bash
python firmware/tools/gfxfont_gen.py <ttf_path> <pt_size> <first> <last> <output.h>
```

Arguments:
- `ttf_path` — path to a TrueType font file
- `pt_size` — point size to rasterise at
- `first` / `last` — decimal ASCII codepoints, e.g. `48 58` for `0..:`
- `output.h` — generated C header file (put in `firmware/src/`)

Example:
```bash
python firmware/tools/gfxfont_gen.py \
  Modak-Regular.ttf 105 48 58 firmware/src/FontModak105.h
```

The output header contains three things:
1. `font_bitmap[]` — 1-bit packed pixel data
2. `font_glyphs[]` — per-glyph metrics table (offset, width, height,
   xAdvance, xOffset, yOffset)
3. `GFXfont font` — the font struct Adafruit GFX uses at runtime

## Step 1: Find a size that fits

The display is **296 px wide × 128 px tall**. A font must fit both
dimensions with readable margins.

### Run the sizing scan

Use this Python snippet against any `.ttf`:

```python
from PIL import ImageFont

path = r"path/to/font.ttf"
display_w = 296
display_h = 128

for pt in [72, 84, 96, 105, 110, 120]:
    font = ImageFont.truetype(path, pt)
    ascent, descent = font.getmetrics()
    line_h = ascent + descent

    bbox0 = font.getbbox('0')
    ink_h = bbox0[3] - bbox0[1]

    w8 = font.getbbox('8')[2] - font.getbbox('8')[0]
    w4 = font.getbbox('4')[2] - font.getbbox('4')[0]
    wc = font.getbbox(':')[2] - font.getbbox(':')[0]
    time_w = w8*2 + w4*2 + wc
    margin = (display_w - time_w) // 2

    print(f"{pt}pt  ink_h={ink_h:2d}  time_w={time_w:3d}  "
          f"margin={margin}px  {'OK' if time_w <= display_w else 'OVERFLOW'}")
```

### Interpretation

| Measure | What it tells you | Target |
|---|---|---|
| `ink_h` | Physical pixel height of a digit (the black part) | **≥ 55 px**, ideally filling 90/128 |
| `time_w` | Width of "88:88" in pixels | **≤ 296** for safe fit; small overflow on worst-case combos like "00:00" is acceptable |
| `margin` | Empty space on each side | **≥ 0 px** for common times like "12:34"; a few pixels of overflow on `08:02` or `00:00` is fine |
| `line_h` | Font's full vertical metrics (ascent + descent) | Can exceed 128 — only the ink matters |



### Understanding the trade-offs

For wide typefaces like Chango, you may not be able to satisfy both
horizontal and vertical fill simultaneously at any single point size.
Chango at 82pt is the practical maximum for 12-hour display (no leading
zero, so "10:00" is the widest string at 293 px):

| Time string | Width | Margin | Fits? |
|---|---|---|---|
| `12:34` | 290 px | 3 px each side | Comfortably |
| `10:00` | 293 px | **1 px** each side | Tight, but OK |
| `8:00` | 238 px | 29 px each side | Plenty of room |

Since `12:34` is the dominant display and the worst case `10:00` still
fits, 82pt gives the best vertical presence (48% ink fill). For 24-hour
mode the widest string is `04:00` (317 px at 82pt) so you'd need to drop
to 74pt to keep 24-hour times within bounds.

### Add the copyright notice

Open the generated header and add the font's copyright line after the
generator comment:

```c
// Generated by gfxfont_gen.py from Modak-Regular.ttf at 105pt
// Range: 0 (0x30) to : (0x3A)
// Copyright (c) 2015 Ek Type (www.ektype.in)
```

You'll find the copyright in the font's metadata (file properties or
the license/readme bundled with the download).

## Step 4: Recalculate the centering

The clock face has three vertical zones:

```
 0 ───── top of display
22 ───── baseline of date line (FreeSans9ptb, y=18 + height ~22)
          ┌─────────────────────┐
          │    TIME HERE        │  ← vertical centre of this gap
          │                     │
110 ──── top of status line  (FreeSans9ptb at display.height - 5)
128 ───── bottom of display
```

The gap between 22 and 110 is **88 pixels**. Its vertical centre is
**66 px** from the top.

Each glyph in `font_glyphs[]` has a `yOffset` field — a negative number
measuring how far above the baseline the glyph's top pixel starts
(Adafruit GFX convention, y-down). To centre the font's ink:

```
baseline_y = 66 - (yOffset + ink_height / 2)
```

Get `yOffset` and `ink_height` from the generated glyph table:

```c
// FontModak105.h glyphs:
{  4961,  31,  56,  33,   0, -106 },   // ':'  →  yOff=-106, h=56
{     0,  61,  69,  63,   0, -106 },   // '0'  →  yOff=-106, h=69
```

Most glyphs share the same yOffset. Use the typical digit values:

```
Modak 105pt:  yOff ≈ -106, h ≈ 69
             → centre offset = -106 + 34.5 = -71.5
             → baseline_y = 66 - (-71.5) ≈ 138
```

Update the `setCursor` call in `drawClockFace()`:

```cpp
// Modak 105pt has typical yOff=-106, h=69. Center of ink relative
// to baseline is -106 + 34.5 = -71.5. Baseline = 66 - (-71.5) = 138.
display.setCursor((display.width() - tw) / 2 - tx, 138);
```

### Common gotcha: colon alignment

After flashing, check whether the colon is **top-aligned** or
**bottom-aligned** relative to the digits. The GFXglyph yOffset
works on a shared baseline — if the colon's yOffset equals the
digits' yOffset, the colon's top sits at the same height as the
digits' top, which usually means the colon hangs high (since it
has no descender).

**Fix:** manually edit the colon's yOffset in the header file.
For Moirai 84pt we moved it from -102 to -86 (raised it 16 px).
For Modak 105pt the colon and digits naturally share yOffset=-106
and it aligned correctly — check what your font needs.

## Generator internals (for debugging)

The script does:

1. Opens the TTF at the requested point size via Pillow
   (`ImageFont.truetype`)
2. Renders each glyph as a 1-bit image
3. Packs pixels MSB-first into a byte array
4. Extracts metrics from `font.getbbox(char)` and
   `font.getmetrics()`
5. Writes the C header with bitmap + glyph table + GFXfont struct

Adafruit GFX renders each glyph by:
- Seeking to `bitmapOffset` in `font_bitmap[]`
- Drawing `width` × `height` pixels starting at
  cursor + (xOffset, yOffset)
- Advancing the cursor by `xAdvance`

The font struct's `yAdvance` is `ascent + descent` from the TTF
metrics, used only for multi-line rendering (not relevant here).
